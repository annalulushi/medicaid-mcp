# CMS Medicaid MCP Server — Design v2

**Date:** 2026-07-20
**Status:** Draft for implementation (supersedes 2026-04-12 draft)
**Changes from v1:** Pivoted from work-requirements-focused to a generic Medicaid/CHIP data explorer; HTTP-first transport on the stateless 2026-07-28 protocol; SDK v2; errors via `ToolError`; structured output; server instructions; rebalanced lens set; MCP Apps as the UI end state; deployment section added.

## Purpose

A Python MCP server wrapping the data.medicaid.gov API (DKAN, OpenAPI 3.0.2, no auth) so Claude — and any MCP client — can explore Medicaid and CHIP datasets conversationally.

This is a **hybrid** design: a thin generic query layer plus a set of curated "lenses" for the recurring questions people actually ask of this data — enrollment trends, drug pricing (NADAC), renewals/unwinding, managed care, and quality measures. Work-requirements readiness (2027, One Big Beautiful Bill Act) remains a supported use case via the enrollment, renewals, and waiver lenses, but is no longer the organizing principle. The generic layer makes ad-hoc questions answerable; the curated lenses make the recurring questions cheap.

The intended end state is a "web app" experience delivered as **MCP Apps** (interactive UI rendered inside Claude/ChatGPT/VS Code by this same server) rather than a separately deployed frontend. See "UI: MCP Apps" below.

This server is distinct from the existing Medicare Coverage MCP (Part B NCDs/LCDs). Different dataset, different audience, separate server.

## Non-Goals

- No standalone web frontend in v1. MCP Apps serve the UI from this server; a public SPA would require an LLM-key proxy, CORS hardening, and real maintenance. Revisit only if we need to reach users outside MCP clients.
- No auth/OAuth. The upstream API is open and the server holds no secrets or user data. If we ever add write-ish features (saved queries, alerts), auth becomes a prerequisite.
- No server-side analytics (pandas transforms, cross-dataset joins, time-series diffing). Premature until real usage reveals which analyses matter.
- No persistent cache (no Redis, no disk). In-memory only; cold starts clear it, and that's fine at our TTLs.
- No live-API integration tests in CI. One manual smoke script instead.
- No config-driven lens definition system in v1. Ship hardcoded lenses first.

## SDK & Protocol

- **Protocol:** target the 2026-07-28 MCP spec revision (stateless request/response; no initialize handshake or protocol-level session). Our design was already stateless, so this is free and it unlocks trivially scalable, load-balancer-friendly hosting.
- **SDK:** official `mcp` Python SDK **v2** (`MCPServer`, the renamed FastMCP class). Stable v2 is targeted for 2026-07-27 alongside the spec release. If we start before stable lands, pin the beta exactly (`mcp==2.0.0bN`) and hold an upper bound `<2.1`. Do **not** start on v1.x — it is in maintenance mode and would mean immediate migration debt on a greenfield repo.
- **Alternative considered:** standalone FastMCP 3.0 (PrefectHQ). Its OpenAPI parser could auto-generate a baseline server from data.medicaid.gov's OpenAPI spec. Rejected for v1: our value-add is precisely the curation (friendly filter DSL, truncation, error hints, lenses) that auto-generation doesn't give us, and the official SDK keeps the dependency surface boring. Revisit if v2 slips or if we want FastMCP's background-tasks/auth batteries later.

## Transport & Deployment

**Streamable HTTP, stateless, JSON responses** (`stateless_http=True, json_response=True`) is the primary transport. stdio remains available for local development (one-line difference at the entrypoint). SSE is deprecated; do not implement it.

Deployment: a single container on a scale-to-zero host. No secrets, no database, no session affinity, so any of Railway, Render, Google Cloud Run, or Prefect Horizon (free personal tier, GitHub CI/CD, FastMCP-native) works; pick by price and deploy ergonomics at implementation time — Cloud Run or Railway are the default candidates. Requirements on the host:

- Respect `PORT` env var; bind `0.0.0.0`.
- Scale-to-zero acceptable: cold starts only cost us the in-memory cache.
- HTTPS endpoint at `/mcp` — this is what users paste into `claude mcp add --transport http` or claude.ai connectors.

Ship a `Dockerfile` and a `fly/railway/cloudrun`-agnostic `uvicorn` entrypoint.

## Architecture

Single Python package. Layout:

```
cms-mcp/
  pyproject.toml
  Dockerfile
  src/cms_medicaid_mcp/
    __init__.py
    server.py          # MCPServer instance, instructions, ASGI app, entrypoints (http + stdio)
    client.py          # DKAN API client (httpx, base URL, error mapping)
    query.py           # Friendly filter shape → DKAN query JSON translator
    cache.py           # TTL cache for /search and dataset metadata
    settings.py        # Env-var-driven configuration
    models.py          # TypedDict/pydantic result shapes (structured output schemas)
    tools/
      __init__.py
      generic.py       # search_datasets, get_dataset, list_dataset_columns, query_dataset
      lenses.py        # Curated tools
    apps/
      __init__.py      # MCP Apps: ui:// resources + tool ↔ resource linking
      ui/              # Bundled HTML/JS for interactive views
  scripts/
    smoke.py           # Manual smoke test against the live API
  tests/
    test_query.py
    test_client.py
    test_tools.py
    test_lenses.py
    fixtures/          # Captured API responses
```

Same four layers with clear boundaries as v1:

- **`client`** knows HTTP — nothing else. Takes request params, returns parsed JSON or raises typed errors.
- **`query`** is pure translation — friendly filter DSL to DKAN query JSON. No network, no state.
- **`tools`** is the MCP surface — validation, calling client/query, shaping responses, raising `ToolError` with hints.
- **`lenses`** composes tools via an internal `_query` helper. **`apps`** attaches UI resources to lens tools without touching query logic.

## Server Instructions

New requirement since April: Claude Code (and other clients adopting tool search) defer MCP tool definitions and use the server `instructions` field to decide when to search for our tools. Write concise instructions (<2KB; clients truncate at 2KB, critical details first) covering:

- What this server does: query US Medicaid/CHIP open data — enrollment, drug pricing (NADAC), drug utilization, renewals, managed care, quality measures.
- When to reach for it: any question about Medicaid/CHIP program data, state comparisons, drug acquisition costs.
- The intended call pattern: `search_datasets` → `list_dataset_columns` → `query_dataset`, or a lens directly for common questions.

Tool descriptions get the same treatment: front-load the essentials, stay well under 2KB.

## Generic Tools

Four tools form the generic MCP surface. All results use typed return models (`models.py`, TypedDict/pydantic) so the SDK emits validated structured output with schemas — no hand-rolled JSON contracts.

### `search_datasets`

**Signature:** `search_datasets(query: str, publisher?: str, keyword?: str, theme?: str, page: int = 1, page_size: int = 20)`

Wraps `GET /api/1/search`. Returns results with `id`, `title`, `description` (truncated to ~300 chars with a `truncated` flag), `publisher`, `modified`, `keywords`, plus `total` and `page_info`. Truncation signals Claude to call `get_dataset` for full metadata. Cached 15 min.

### `get_dataset`

**Signature:** `get_dataset(dataset_id: str)`

Wraps `GET /api/1/metastore/schemas/dataset/items/{id}`. Returns full metadata **plus** a synthesized `columns` array (name, type, sample values) so Claude can construct a valid `query_dataset` call without guessing. Cached 1 hour.

### `list_dataset_columns`

**Signature:** `list_dataset_columns(dataset_id: str)`

Just the `columns` array. Kept separate because it's the single most common orientation call and cheaper in tokens than the full metadata blob. Shares the `get_dataset` cache entry.

### `query_dataset`

**Signature:**

```
query_dataset(
  dataset_id: str,
  filters?: list[{column, op, value}],
  columns?: list[str],
  sort?: list[{column, direction}],
  limit: int = 50,
  offset: int = 0,
)
```

Supported ops: `=`, `!=`, `<`, `<=`, `>`, `>=`, `in`, `like`. Server translates to DKAN `/datastore/query` JSON. Hard cap `limit ≤ 500` (DKAN limit), but the **default drops from 100 to 50**: clients now warn at ~10K tokens of tool output and cap at ~25K by default, and 100 rows of a wide dataset can blow that. Returns `rows`, `total`, `next_offset`, `schema`. Responses should nudge pagination ("N of M rows; call again with offset=…") rather than dumping maximal data. Not cached — freshness matters and cache keys get messy with filter combos.

## Error Handling

**Changed from v1:** no `{error: {code, message, hint}}` result shape. Use the protocol's error channel — raise `ToolError` (returned to the client with `isError=True`) with the hint folded into the message:

> `Unknown column 'stat' for dataset X. Call list_dataset_columns("X") to see valid columns. Did you mean 'state'?`

`client.py` still maps httpx exceptions to typed errors (`ApiTimeout`, `ApiHttpError`, `ApiPayloadError`); tools catch these and re-raise as `ToolError` with actionable messages (retry hint for network errors; next-call hint for 4xx).

## Curated Lenses (v1 of v2)

Rebalanced for the generic pivot. Each remains ~30 lines composing the internal `_query` helper — one code path for query construction.

**Caveat (unchanged and still the first implementation task):** targets assume dataset shapes we haven't verified. The dataset discovery pass against the live API confirms or replaces each lens; gaps get documented.

**Enrollment & eligibility**

1. **`get_state_enrollment_snapshot(state, months_back=12)`** — most recent monthly Medicaid/CHIP enrollment for one state.
2. **`compare_states_enrollment_trend(states, months_back=24)`** — multi-state, shaped for summarization or charting (and for the MCP Apps chart view).
3. **`get_state_eligibility_renewals(state, months_back=12)`** — renewal/termination churn. Still the best readiness proxy for 2027 work requirements; equally useful for general unwinding analysis.

**Drug pricing & utilization** _(new — likely the most-used datasets on the site)_

4. **`get_drug_price_nadac(drug_name_or_ndc, months_back=12)`** — National Average Drug Acquisition Cost lookups; NADAC updates weekly.
5. **`get_state_drug_utilization(state, drug_name_or_ndc?, year?)`** — State Drug Utilization Data: units, prescriptions, Medicaid amounts reimbursed.

**Program structure & quality** _(new)_

6. **`get_managed_care_enrollment(state?, year?)`** — enrollment by plan/program type per state.
7. **`get_quality_measures(state, measure_set: "child"|"adult", year?)`** — Child/Adult Core Set performance measures.

**Cross-cutting**

8. **`whats_new_medicaid(since, categories?)`** — recently modified datasets via `/search` sorted by `modified`.

**Deferred, pending discovery:** `list_1115_waivers` — retained as a candidate because waiver activity is the leading indicator for 2027 work requirements, but waiver data may live on the CMS side of Medicaid.gov rather than data.medicaid.gov. If discovery confirms it's absent, drop it and document the gap rather than substituting a weak proxy.

## UI: MCP Apps

The "simple and intuitive web app" ships as **MCP Apps** (official MCP extension, live since 2026-01-26; supported by Claude web/desktop, VS Code Copilot, ChatGPT, Goose, and others). Interactive HTML views are served by this server as `ui://` resources and linked from tools via `_meta.ui.resourceUri`; the host renders them in-conversation in a sandboxed iframe.

Why this beats a standalone web app for us: zero extra deployment (same container), zero LLM API costs (the user's client supplies the model), no auth, no tab-switching, and it works across multiple hosts from one codebase.

Phased:

- **v1:** no UI. Ship tools; structured output already makes results chart-ready.
- **v1.1:** two views — an enrollment trend chart (backing lenses #1/#2) and a NADAC price-history chart (lens #4). Static bundled HTML/JS, no build pipeline beyond copying files.
- **Later, if earned:** a dataset browser view over the generic tools.

UI is additive: every tool must remain fully useful as text/structured output for hosts without Apps support (e.g., Claude Code).

## Data Flow

Unchanged from v1:

```
Claude → tools/generic.query_dataset (validate) → query.translate → client.datastore_query (httpx) → shaped result
```

Lenses call the internal `_query(dataset_id, ...)` helper directly.

## Caching

In-memory TTL cache in `cache.py`. `search_datasets` 15 min; dataset metadata 1 hour; row data never. Process-local; restarts and scale-to-zero cold starts clear it, which is acceptable.

## Configuration

Single `Settings` object from env vars:

| Variable                        | Default                                         |
| ------------------------------- | ----------------------------------------------- |
| `CMS_MEDICAID_BASE_URL`         | `https://data.medicaid.gov`                     |
| `CMS_MEDICAID_TIMEOUT`          | `30` (seconds)                                  |
| `CMS_MEDICAID_CACHE_TTL_SEARCH` | `900`                                           |
| `CMS_MEDICAID_CACHE_TTL_META`   | `3600`                                          |
| `CMS_MEDICAID_LOG_LEVEL`        | `INFO`                                          |
| `PORT`                          | `8000` (HTTP transport; honored for PaaS hosts) |

No secrets, no key file — API is open.

## Testing

- **`test_query.py`** — pure unit tests on the filter DSL translator. Table-driven, no network.
- **`test_client.py`** — httpx `MockTransport` with captured fixtures under `tests/fixtures/`.
- **`test_tools.py` / `test_lenses.py`** — end-to-end through the SDK's in-memory client↔server session (no subprocess, no HTTP): assert structured output shapes, `isError` results, and hint text.
- **MCP Inspector** for interactive dev against both transports.
- **`scripts/smoke.py`** — manual live-API smoke test; not in CI.

TDD throughout. Order: `query.py` → `client.py` error mapping → tools → lenses.

## Open Questions (resolve during discovery)

- Do 1115 waivers live on data.medicaid.gov at all? If not, drop lens; document.
- Is enrollment data monthly as lenses #1/#2 assume? Adjust signatures if quarterly/other.
- NADAC and State Drug Utilization column shapes — NDC formats, name matching (`like` vs. exact), and whether NADAC history requires querying multiple distributions.
- Does `/metastore/schemas/dataset/items/{id}` include column schema directly, or does `get_dataset` need a follow-up `/datastore/schema/{distributionId}` call?
- v2 SDK stable timing: if 2026-07-27 slips materially, decide between staying on a pinned beta vs. switching to standalone FastMCP 3.0.
