## Decisions to settle before writing code

These block step 1 and should not be deferred into it.

1. **Package name.** The design doc says `cms-mcp` / `src/cms_medicaid_mcp/`; the repo, the `pyproject.toml` `name`, and the GitHub URL all say `medicaid-mcp`. **Recommendation: `src/medicaid_mcp/`** — it matches the distribution name already published in `pyproject.toml` and avoids a rename later. Adopt or overrule explicitly; do not let the two names coexist.
2. **Build backend.** No `[build-system]` exists, so uv currently treats this as a non-packaged project and `license-files` is inert. Adding a `src/` package requires one. **Recommendation: hatchling** — smallest config for a `src/` layout.
3. **SDK version, verified not assumed.** See step 0.

## Step 0 — Re-verify the aged assumptions

The design doc was written 2026-07-20 against dates that have since passed. Confirm each against primary sources **before** pinning anything. Do not treat the doc's predictions as facts.

- Did the official `mcp` Python SDK v2 ship stable? The doc targeted 2026-07-27. If it slipped, the doc's own fallback applies: pinned beta vs. standalone FastMCP 3.0 (design doc, "Open Questions", last bullet).
- Did the 2026-07-28 protocol revision land as specified, and is stateless request/response in it as described?
- Is `MCPServer` the actual class name in the shipped v2 API, and do `stateless_http` / `json_response` still exist as constructor kwargs?
- Does data.medicaid.gov still serve the documented DKAN endpoints (`/api/1/search`, `/api/1/metastore/schemas/dataset/items/{id}`, `/datastore/query`)?

**Done when:** each of the four has a verified yes/no recorded in this doc, and the exact version pin for `mcp` is chosen. **If any answer is no, stop and amend the design doc before coding** — a wrong SDK pin invalidates steps 5, 6, and 8.

## Step 1 — Scaffold the package

Create `src/medicaid_mcp/` with the module skeleton from the design doc's Architecture section, plus `tests/` and `scripts/`. Add `[build-system]`, the verified `mcp` pin with its `<2.1` bound, `httpx`, and dev dependencies (`pytest`, `pytest-asyncio`, `ruff`, `mypy`). Delete `main.py` — it is `uv init` residue and nothing imports it. Commit `uv.lock`.

**Done when:** `uv sync` succeeds, `uv run python -c "import medicaid_mcp"` succeeds, `uv run pytest` collects zero tests without error.

## Step 2 — Dataset discovery pass *(moved up from 7th)*

**Why this moved.** The design doc puts discovery at step 7, but step 3 calls for `test_client.py` driven by "captured fixtures under `tests/fixtures/`" — and those fixtures are exactly what discovery produces. Running discovery seventh would mean either hand-writing fixtures that may not match reality, or blocking step 3. Discovery is also read-only, needs no auth, and answers four of the five open questions, so it is the cheapest possible de-risking. It belongs first.

Against the live API: confirm or replace each of the eight lens targets, capture real responses into `tests/fixtures/`, and record the actual column shapes. Resolve the design doc's open questions:

- Do 1115 waivers exist on data.medicaid.gov? If not, drop `list_1115_waivers` and **document the gap — do not substitute a weak proxy** (design doc's explicit instruction).
- Is enrollment monthly, as lenses #1/#2 assume?
- NADAC / State Drug Utilization column shapes: NDC formats, `like` vs. exact matching, whether NADAC history spans multiple distributions.
- Does `/metastore/schemas/dataset/items/{id}` carry column schema directly, or is a follow-up `/datastore/schema/{distributionId}` call needed? This determines whether `get_dataset` is one request or two.

**Done when:** every lens has a named, verified dataset ID or a written rationale for being dropped; fixtures are committed; the open-questions list is answered in writing.

## Step 3 — `query.py` + `test_query.py`

Pure translation: friendly filter DSL → DKAN query JSON. No network, no state. Ops `=`, `!=`, `<`, `<=`, `>`, `>=`, `in`, `like`. Table-driven tests including rejection cases (unknown op, bad types, `limit > 500`).

**Done when:** tests pass, module imports nothing from `client`, and invalid input raises rather than silently coercing.

## Step 4 — `client.py` + `test_client.py`

httpx client for the three endpoints. Maps httpx exceptions to typed errors `ApiTimeout`, `ApiHttpError`, `ApiPayloadError`. Tested with `MockTransport` over the step-2 fixtures.

**Done when:** every error path has a test asserting the typed error — including a malformed-payload case. No bare `except`, and no code path returns an empty result where an error occurred.

## Step 5 — `cache.py`, `settings.py`, `models.py`

In-memory TTL cache (search 15 min, metadata 1 hour, rows never). `Settings` from the six documented env vars. Typed result shapes for structured output.

**Done when:** TTL expiry is unit-tested with an injected clock (no `sleep`), and `Settings` defaults match the design doc's table exactly.

## Step 6 — Generic tools + `test_tools.py`

`search_datasets`, `get_dataset`, `list_dataset_columns`, `query_dataset`. Each raises `ToolError` with the recovery hint folded into the message — never a success-shaped error payload. Tested through the SDK's in-memory client↔server session.

**Done when:** tests assert both structured output shapes and `isError` results with hint text, and `query_dataset` nudges pagination rather than dumping maximal rows.

## Step 7 — `server.py` + `Dockerfile`

`MCPServer` with the <2KB instructions string; stdio and streamable-HTTP entrypoints; `uvicorn` entrypoint honoring `PORT` and binding `0.0.0.0`. No SSE.

**Done when:** MCP Inspector connects over both transports and lists all four tools; `docker run -e PORT=8000` serves `/mcp`.

## Step 8 — Lenses + `test_lenses.py`

Implement the lenses that survived step 2, each composing the internal `_query` helper. Dropped lenses get a line in the design doc explaining why.

**Done when:** every surviving lens has a test over real fixtures, and the count of shipped lenses plus documented drops equals eight.

## Step 9 — Deploy

Cloud Run or Railway. Run `scripts/smoke.py` against the deployed URL. Update the README: remove the design-only banner, add real `claude mcp add --transport http` and claude.ai connector instructions.

**Done when:** a fresh MCP client connects to the public `/mcp` URL and completes `search_datasets` → `list_dataset_columns` → `query_dataset` end to end. **The README banner comes off only after this passes** — not before.

## Step 10 — *(v1.1)* MCP Apps

Enrollment trend chart (lenses #1/#2) and NADAC price-history chart (lens #4) as `ui://` resources. Every tool must stay fully useful as text for hosts without Apps support.

## Critical path

```
0 (verify) → 1 (scaffold) → 2 (discovery) → 3 (query) → 4 (client) → 5 (infra) → 6 (tools) → 7 (server) → 8 (lenses) → 9 (deploy) → 10 (UI)
```

Steps 3 and 5 are independent of each other and can run in parallel. Everything else is strictly sequential. Step 0 gates all of it.

## Risks

| Risk | Impact | Response |
| --- | --- | --- |
| `mcp` v2 stable never shipped | Steps 5–8 rework | Resolve at step 0, before any pin |
| Lens datasets don't exist or differ in shape | Step 8 shrinks | Step 2 finds this early; document gaps, don't fake substitutes |
| DKAN schema needs a second request per dataset | `get_dataset` latency doubles | Answered at step 2; adjust caching if so |
| Scope creep into analytics or a web frontend | Timeline | Both are explicit non-goals in the design doc |
