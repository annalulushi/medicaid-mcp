## Decisions to settle before writing code

These block step 1 and should not be deferred into it.

1. **Package name — SETTLED 2026-09-23: `src/medicaid_mcp/`.** Overrules the design doc's `cms-mcp` / `src/cms_medicaid_mcp/`. `medicaid_mcp` matches the distribution name in `pyproject.toml`, the repository, and the GitHub URL, so import path and project name agree and no rename is needed later. The design doc's Architecture section is stale on this point; treat this line as authoritative.
2. **Build backend — SETTLED 2026-09-23: `hatchling`.** No `[build-system]` exists, so uv currently treats this as a non-packaged project and `license-files` is inert. Adding a `src/` package requires one.

   Tested empirically (2026-09-23): `hatchling`, `uv_build`, and `setuptools>=77` were each given the real `pyproject.toml` with `license = "MIT"` / `license-files = ["LICENSE"]` and a `src/medicaid_mcp/` layout.

   | Backend          | Build | `src/` autodetected | LICENSE in wheel | Extra config needed |
   | ---------------- | ----- | ------------------- | ---------------- | ------------------- |
   | `hatchling`      | OK    | yes                 | yes              | none                |
   | `uv_build`       | OK    | yes                 | yes              | none                |
   | `setuptools>=77` | OK    | yes                 | yes              | none                |

   All three need zero extra configuration, so config size does not discriminate. The decision rests on this: hatchling is mature and backend-agnostic, so the step-7 `Dockerfile` can install with plain `pip` and is not coupled to having uv in the build image. `uv_build` is the runner-up and is meaningfully faster; revisit it if the Docker image standardizes on uv anyway. `setuptools` carries the largest legacy surface for no gain here.

3. **Env-var prefix — SETTLED 2026-09-23: `MEDICAID_MCP_*`.** Overrules the design doc's `CMS_MEDICAID_*`, for the same reason as the package name: prefix, import path, and distribution name agree. The five prefixed variables are `MEDICAID_MCP_BASE_URL`, `MEDICAID_MCP_TIMEOUT`, `MEDICAID_MCP_CACHE_TTL_SEARCH`, `MEDICAID_MCP_CACHE_TTL_META`, `MEDICAID_MCP_LOG_LEVEL`; `PORT` stays unprefixed because hosting platforms set it. Names change only — defaults are unchanged from the design doc's Configuration table. The README's Configuration table carries the settled names and defaults and is the reference for step 5.
4. **SDK version — OPEN.** Must be verified, not assumed. See step 0.

### Verified: data.medicaid.gov API, 2026-09-23

All three endpoints — `/api/1/search`, `/api/1/metastore/schemas/dataset/items/{id}`, and `/api/1/datastore/query/{distributionId}` — return HTTP 200. The catalog holds **277 datasets**. Five findings contradict or sharpen the design doc, and each one changes code:

1. **`search` returns `results` as a JSON object keyed by dataset URI, not an array.** The design doc's result shaping assumes a list. `models.py` and `search_datasets` must iterate `.values()`.
2. **The dataset id field is `identifier`, not `id`.** The design doc's `search_datasets` return spec says `id`. Either rename in our model or map explicitly — do not let both names float.
3. **Column schema is NOT in the metastore item.** This answers the design doc's fourth open question: the metastore item returns no `describedBy` and no field list. Schema comes back from the datastore query endpoint. So **`get_dataset` needs two requests**: metastore item → distribution `identifier` → datastore query. This raises the value of the 1-hour metadata cache.
4. **`?show-reference-ids` is required** to get a distribution `identifier` out of the metastore item at all. Without it the distribution block has no id and the datastore is unreachable. Easy to miss; hard to debug.
5. **`limit` is not capped at 500 by the API.** `limit=501` returned 501 rows, and `limit=0` returned **HTTP 400**. The design doc calls 500 a "DKAN limit" — it is not; it is _our_ cap and we must enforce it ourselves. `list_dataset_columns` must use `limit=1`, never `limit=0`.

**Also confirmed:** lens #6 has a real target — "Managed Care Enrollment by Program and Plan" (`0bef7b8a-c663-5b14-9a46-0b5c2b86b0fe`, 7,804 rows) with columns `state`, `year`, `program_name`, `plan_name`, `total_enrollment`, `dual_enrollment`.

**Warning for step 3:** every column in that dataset types as `text` in the datastore schema — including enrollment counts and `year`. Numeric filters (`<`, `>`, `<=`, `>=`) against text columns compare lexically, so `"9" > "10"`. The filter DSL must either cast or refuse numeric ops on text columns rather than silently returning wrong rows. Step 2 measures how widespread this is.

## Step 2 — Dataset discovery pass _(moved up from 7th)_

**Why this moved.** The design doc puts discovery at its step 7, but `test_client.py` (step 4 here) is driven by "captured fixtures under `tests/fixtures/`" — and those fixtures are exactly what discovery produces. Step 3's handling of `text`-typed columns also depends on what discovery finds. Running discovery late would mean either hand-writing fixtures that may not match reality, or blocking those steps. Discovery is also read-only and needs no auth, so it is the cheapest possible de-risking.

Against the live API: confirm or replace each of the eight lens targets (lens #6 is already confirmed), capture real responses into `tests/fixtures/`, and record the actual column shapes. Resolve the design doc's remaining open questions:

- Do 1115 waivers exist on data.medicaid.gov? This decides the deferred candidate lens `list_1115_waivers`. If absent, drop it and **document the gap — do not substitute a weak proxy** (design doc's explicit instruction).
- Is enrollment monthly, as lenses #1/#2 assume?
- NADAC / State Drug Utilization column shapes: NDC formats, `like` vs. exact matching, whether NADAC history spans multiple distributions.
- How widespread is the all-`text` column typing seen in the managed-care dataset? Determines whether the filter DSL casts or refuses numeric ops.

(The design doc's fourth open question — whether the metastore item carries column schema — was answered at step 0: it does not. Its fifth, SDK timing, is step 0's job.)

**Done when:** every lens has a named, verified dataset ID or a written rationale for being dropped; `list_1115_waivers` is either promoted with a dataset ID or dropped with a rationale; fixtures are committed; the open questions above are answered in writing in this doc; and the README's "Planned lenses" section reflects the outcome (which lenses are verified, whether `list_1115_waivers` is in or out).

## Step 3 — `query.py` + `test_query.py`

Pure translation: friendly filter DSL → DKAN query JSON. No network, no state. Ops `=`, `!=`, `<`, `<=`, `>`, `>=`, `in`, `like`. Table-driven tests including rejection cases (unknown op, bad types, `limit > 500`, `limit < 1`).

Carries three step-0 findings:

- The 500 cap is **ours to enforce** — the API accepts more.
- `limit=0` is an API 400, so `limit < 1` raises before any request is built. Do not clamp: clamping is silent coercion.
- Numeric ops against `text`-typed columns must cast or raise, per step 2's finding — never compare lexically and return plausible-looking wrong rows.

**Done when:** tests pass, module imports nothing from `client`, and every invalid input raises rather than being coerced.

## Step 4 — `client.py` + `test_client.py`

httpx client for the three endpoints listed under step 0, always sending `?show-reference-ids` on metastore requests. Maps httpx exceptions to typed errors `ApiTimeout`, `ApiHttpError`, `ApiPayloadError`. Tested with `MockTransport` over the step-2 fixtures.

**Done when:** every error path has a test asserting the typed error — including a malformed-payload case and a metastore item with no distribution `identifier`. No bare `except`, and no code path returns an empty result where an error occurred.

## Step 5 — `cache.py`, `settings.py`, `models.py`

In-memory TTL cache (search 15 min, metadata 1 hour, rows never). `Settings` from the six env vars, using the settled `MEDICAID_MCP_*` names. Typed result shapes for structured output, using `identifier` (finding 2) and iterating `search` results as an object (finding 1).

**Done when:** TTL expiry is unit-tested with an injected clock (no `sleep`), `Settings` names and defaults match the README's Configuration table exactly, and a test asserts the old `CMS_MEDICAID_*` names are not read.

## Step 6 — Generic tools + `test_tools.py`

`search_datasets`, `get_dataset` (two requests, per finding 3), `list_dataset_columns` (`limit=1`, per finding 5), `query_dataset`. Each raises `ToolError` with the recovery hint folded into the message — never a success-shaped error payload. Tested through the SDK's in-memory client↔server session.

**Done when:** tests assert both structured output shapes and `isError` results with hint text, and `query_dataset` nudges pagination rather than dumping maximal rows.

## Step 7 — `server.py` + `Dockerfile`

The step-0-verified server class (`MCPServer` if confirmed) with the <2KB instructions string; stdio and streamable-HTTP entrypoints; `uvicorn` entrypoint honoring `PORT` and binding `0.0.0.0`. No SSE.

**Done when:** MCP Inspector connects over both transports and lists all four tools; `docker run -e PORT=8000` serves `/mcp`.

## Step 8 — Lenses + `test_lenses.py`

Implement the lenses that survived step 2, each composing the internal `_query` helper. Dropped lenses get a line in the design doc explaining why.

**Done when:** every surviving lens has a test over real fixtures, and every one of the nine candidates (the eight lenses plus `list_1115_waivers`) is either shipped or has a documented drop.

## Step 9 — Deploy

Cloud Run or Railway. Run `scripts/smoke.py` against the deployed URL. Update the README: remove the design-only banner, drop "Planned" from section headings for what shipped, and add real `claude mcp add --transport http` and claude.ai connector instructions to "Local development".

**Done when:** a fresh MCP client connects to the public `/mcp` URL and completes `search_datasets` → `list_dataset_columns` → `query_dataset` end to end. **The README banner comes off only after this passes** — not before.

## Step 10 — _(v1.1)_ MCP Apps

Enrollment trend chart (lenses #1/#2) and NADAC price-history chart (lens #4) as `ui://` resources. Every tool must stay fully useful as text for hosts without Apps support.

## Critical path

```
0 (verify) → 1 (scaffold) → 2 (discovery) → 3 (query) → 4 (client) → 5 (infra) → 6 (tools) → 7 (server) → 8 (lenses) → 9 (deploy) → 10 (UI)
```

Steps 3 and 5 are independent of each other and can run in parallel. Everything else is strictly sequential. Step 0 gates all of it.
